## Алхам 3: Сценариос SLO

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | /cart/add latency | p95 < 50 мс | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | /pay error rate | < 8% | 1 мин, 20 VU |
| Availability | бүх хүсэлтийн амжилтын хувь | >= 90% | 2 мин, 10 с зогсолт орсон |

**Босгын үндэслэл**

- Performance: 20 VU дээр хэмжсэн baseline p95 = 1.25 мс (results/pass.txt; тусдаа baseline-cart.txt хэмжилт хийгээгүй тул хэвийн ачаалалтай pass тестийн утгыг авав). Босгыг baseline p95 x 1.5-аар тооцож, localhost-ийн санамсаргүй саатлаас болж байнга FAIL болохоос сэргийлж 50 мс-ээс доош оруулаагүй тул 50 мс болсон.
- Reliability: серверт зориудаар ~5% алдаа суулгасан. 1 минутын 20 VU тест ~1200 хүсэлт үүсгэх бөгөөд алдааны хувийн стандарт хазайлт ойролцоогоор 0.6% (sqrt(0.05 x 0.95 / 1200)) тул 8% нь 5%-иас ойролцоогоор 4.7 стандарт хазайлтаар дээр байна. Иймээс 8% нь санамсаргүй хэлбэлзлээс болж FAIL болохгүй, харин алдааны түвшин бодитоор нэмэгдвэл илрүүлэх бодит босго юм.
- Availability: 10 секундийн зогсолтыг тэсвэрлэх тул 2 минутын цонхонд 90%-ийг сонгосон.

**Availability-ийн error budget (ЦАГААР)**

2 минут = 120 секунд. SLO 90% бол 10% нь эвдрэх эрхтэй: 120 с x 0.10 = **12 секунд**. Төлөвлөсөн 10 секундийн зогсолт энэ budget-ийн 10 / 12 = 83%-ийг зарцуулна, 2 секунд л нөөц үлдэнэ. Хэрэв сервер 12 секундээс удаан сэргэвэл SLO зөрчигдөнө. Энэ нь хугацаагаар тооцсон budget бөгөөд Алхам 5-д хүсэлтээр дахин тооцож, хоёр тоо яагаад зөрж байгааг тайлбарлана.

## Алхам 4: SLO → k6 threshold (slo-test.js)

| SLO | k6 threshold | Зорилго |
|---|---|---|
| Performance: /cart/add p95 | http_req_duration{name:cart}: p(95)<босго (README-ийн Алхам 3 хүснэгттэй ижил) | latency |
| Reliability: /pay error rate < 8% | http_req_failed{name:pay}: rate<0.08 | алдааны хувь |
| Availability: амжилтын хувь >= 90% | checks: rate>0.90 | бүх хүсэлтийн амжилт |
| Нэмэлт: /report p95 < 450 мс | http_req_duration{name:report}: p(95)<450 | удаан endpoint |

/report-ийн босго: сервер 200-400 мс санамсаргүй хүлээдэг тул p95 нь ойролцоогоор 395-405 мс, дээд хязгаар 400 мс дээр 12.5%-ийн нөөц нэмж 450 мс болгосон.

Нэг тэмдэглэл: checks threshold нь одоогоор зөвхөн /pay-ийн санамсаргүй 500-г тоолдог (~2% нь нийт check-ээс). Жинхэнэ crash-ийн availability-г Алхам 5-д серверийг зогсоож хэмжинэ.

Үр дүн: results/pass.txt (бүх threshold PASS, exit code 0), results/fail-step4-strict.txt (санаатай хатуу threshold FAIL, exit code 99).
## Дүгнэлт

1. Сценариос SLO руу шилжихэд хамгийн хэцүү нь босго тоог бодитоор сонгох байсан: localhost дээр /cart/add-ийн baseline p95 = 1.25 мс тул зааврын жишээ 200 мс нь юу ч хэмжихгүй сул босго болох байсан.
2. Тиймээс Performance босгыг baseline p95 x 1.5-аар тооцож, localhost-ийн санамсаргүй саатлаас болж байнга FAIL болохоос сэргийлж 50 мс-ээс доош оруулаагүй, эцсийн босго p95 < 50 мс болсон бөгөөд pass.txt-д хэмжсэн 1.25 мс байлаа.
3. Reliability сценарийн босго 8% нь суулгасан ~5% алдааны дээр ~4.7 стандарт хазайлтын нөөц нэмсэн утга бөгөөд pass.txt-д /pay-ийн error rate 5.27% гарч SLO хангагдсан.
4. /report-ийн p(95)<450 мс босго нь серверийн 200-400 мс хүлээлтэд 12.5%-ийн нөөц нэмсэн утга бөгөөд pass.txt-д 389.77 мс гарсан.
5. Алхам 5-д серверийг 30 секундэд зогсоож ~10 секундийн дараа дахин асаахад (MTTR = 10.1 с, results/chaos-mttr.txt) availability = 5008 / 5697 = 87.91% гарч 90%-ийн SLO **зөрчигдсөн** (checks threshold FAIL, exit code 99, results/chaos.txt). MTTR <= 15 с шаардлага хангагдсан ч цагаар тооцсон 12 секундийн budget-д багтсан зогсолт хүсэлтээр тооцсон budget-д багтаагүй.
6. Хэмжсэн 5697 хүсэлтээс 689 нь амжилтгүй болсон нь хүсэлтээр тооцсон 10%-ийн error budget (570 хүсэлт)-тэй харьцуулагдах бөгөөд энэ нь цагаар тооцсон 12 секундийн budget-ээс ялгаатай, учир нь зогсолтын үед хүсэлт агшин зуур буцдаг тул нэг секундэд хэвийн үеийнхээс олон хүсэлт гардаг.
7. Нэг crash нь /pay-ийн хүсэлт бүрийг унагадаг тул availability болон reliability хоёр SLO-г зэрэг зөрчдөг, иймд SLI-гээ "хариу огт ирээгүй (status 0)" ба "5xx хариу ирсэн" гэж тусгаарлах нь шийдэл юм.
8. Мөн checks threshold нь /pay-ийн санамсаргүй 500-г availability-д хольж тоолдог нь SLO-г threshold болгох үеийн нарийн алдаа боллоо.
9. slo-test-fail.js-д /report p(95)<100 нь exit code 99-өөр FAIL болсон нь CI pipeline-ийн quality gate-ийн зарчим, харин /cart/add p(95)<50 нь localhost дээр хэзээ ч FAIL болохгүй тул шалгалт болж чадахгүй.
10. Иймээс сайн SLO нь сценариогийн бодит хэмжилтэд (baseline, бодит алдааны хувь) тулгуурлаж, хүсэлт болон цагийн хэмжигдэхүүнийг хольж андуурахгүй, мөн тестээр дахин шалгагдах ёстой гэж дүгнэв.
